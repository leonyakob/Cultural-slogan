## 一、当前状态：PROJECT_PLAN.md 已不完全符合用户想法

现有 PROJECT_PLAN.md（v0.3）的基调是"**Agent 负责流程编排、Skill 负责方法规则**"（第 10 节已确认决策第 5 条），实现路线五个阶段中有三个（阶段二、三、四）围绕 Skill 与 Agent 展开。

用户现在的判断：**当初想做 skill 和 agent 的想法太仓促且不理智**。全程可能根本不需要 skill 和 agent；即使将来需要，到时再重新设计也来得及。因此整体规划不应把 skill 和 agent 说死。

**本讨论的目标**：在对话中把想法聊透，然后由用户重新设计项目走向。讨论过程与结论全部存放在 `项目讨论/` 文件夹下。

## 二、三个诉求

### 诉求 1：解绑 Skill/Agent

- 原设想：做出一个 skill + agent 组成的、自动产出口号的 agent。
- 现在的判断：这一设想仓促且不理智；有可能全程不需要 skill 和 agent。
- **待聊透的问题**：
  - "不需要 skill/agent"的判断依据是什么——是觉得流程本身不需要自动化，还是觉得当前形态（人工驱动对话）已经够用？
  - 现有规划中哪些内容是"方法本身"（与 skill/agent 无关、值得保留），哪些是"为 skill/agent 服务的实现细节"（可剥离）？
  - 保留到什么程度算是"没说死"——是规划里完全不提，还是留一个不预设形式的扩展位？

### 诉求 2：整体规划调整

- 前提：先不考虑 agent 和 skill。
- **待聊透的问题**：
  - 调整后的项目形态是什么：一个人 + Claude 对话按流程推进？还是文档化的工作手册，谁来执行都行？
  - 五阶段实现路线（方法协议 → 方法型 Skill → 真实项目验证 → 编排 Agent → 评估迭代）去掉中间两环后还剩什么顺序？
  - 总流程 11 步（立项→…→投稿输出）本身是否受影响？哪些步骤是"方法步骤"（保留），哪些是"编排步骤"（形式待定）？
  - 质量标准、真实性协议、证据四态这些方法层内容应该原样保留还是也要调整？

### 诉求 3：模块衔接与内部运转

- 用户需要先搞清楚：**各模块之间如何衔接、各模块内部如何运转**。
- 已有的讨论基础（本对话前半段，围绕临安素材）：
  - 31 份文档分成两类数据：征集令 = 任务规格书（提取口号要求），其余 30 篇 = 素材语料库（提取城市特色），两类用完全不同的处理逻辑；
  - 衔接设计：两条管线各自独立，通过窄接口汇合——共享 `destination` / `task_id` 字段 + 征集令产出的维度受控词表（吴越文脉/天目生态/文旅体融合）作为素材打标体系 + 内容分类→征集维度映射表；
  - 汇合点：R0 研究任务定义、R3/R4 素材打标、R7 核心认知候选、阶段 8/10 批判与验证、阶段 11 投稿阐述；
  - MVP 形态落地为三个文件：约束矩阵.md、证据台账.md（含 dimension 列）、分类映射.md。
- **待聊透的问题**：
  - 已规划的模块只有"目的地研究与证据审计"一个（R0-R8）。口号生成、批判筛选、投稿阐述这些后续环节要不要也成模块？模块边界怎么划？
  - 模块间传递的"数据契约"（上一轮聊的窄接口）是否就是衔接的答案，还是还需要流程层面的衔接（谁先谁后、回退怎么走）？
  - "模块内部如何运转"对人工驱动的会话意味着什么——是一次对话跑完一个模块，还是一份模块内 checklist？

## 四、结论区（随讨论填充）

### 诉求 1 结论

**用户直觉：1 和 2 的混合，2 略高**——即"不预设载体，用真实项目跑完后的痛点驱动"（主），叠加"流程人工判断密度高、对话+文档可能就是最终形态"（辅）。

**由此确认的分离原则**：项目内容分两层——

- **方法层**（与 skill/agent 无关，保留）：流程 11 步的问题序列、真实性协议与证据四态、研究充分性闸门、用户决策节点、质量标准；
- **载体层**（解绑，不预设）：Agent/Skill 职责划分、实现路线的阶段二/四、为自动化预留的措辞。

**载体决策规则**：不预先决定是否需要 skill/agent。用当前形态（人工对话 + 方法文档）跑完临安真实项目，哪里痛、哪里值得固化，再决定——固化形式也不限于 skill/agent，可能是模板、checklist、脚本或什么都不是。

### 诉求 2 结论

**核心叙事转换**：从"构建一个系统"（工作台、Agent 编排、Skill 内核、五阶段路线）转为"**一套可演进的方法 + 一个真实项目的验证过程**"。

**用户纠正的关键细节**：方法不是固定不变地被"验证"——它是**开放演进**的：任何更好的方案都可以随时插入或优化，真实项目跑的过程既是验证也是改进方法的机会。验证不是终点式验收，而是持续演化。

**调整轮廓（已确认）**：

1. **项目定义重写（1.1）**：主语从"协作型 Agent"改为"工作流程"；人与 AI 的关系是"人驾驶、AI 副驾"，不是"委托给 Agent"。
2. **五阶段实现路线（第 8 节）重写为三段**：方法协议 → 真实项目验证（临安为第一个，过程记录顺/滞/返工）→ 回顾与固化决策（逐项决定：改方法 / 固化为模板 / 值得自动化 / 不动）。
3. **第 6 节职责划分改按"决策权"而非角色**：必须用户做（锁定方案、否决方向）/ 可交给 AI（资料整理、初筛、起草）/ 流程规则（闸门、回退）。将来若做 skill/agent，职责矩阵直接平移。
4. **保留不动**：真实性协议（4.4）、质量标准（7）、不可行终局、用户决策节点、9.6 跨项目方法资产——方法层与载体无关。
5. **第 10 节决策第 5 条改写**："项目当前不预设任何自动化载体；方法以文档形态维护，载体决策延后到首个真实项目完成后。"
